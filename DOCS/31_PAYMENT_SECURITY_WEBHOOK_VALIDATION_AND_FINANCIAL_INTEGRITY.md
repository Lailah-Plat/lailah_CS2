# 💳 وثيقة أمان المدفوعات، التحقق الرقمي من الـ Webhooks والسلامة المالية السيادية
**Payment Security Standard, Cryptographic Webhook Validation, Anti-Fraud & Sovereign Financial Integrity**

---

## 1. أمان المدفوعات والربط المعياري مع بوابات الدفع (Payment Gateway Security Standard)

تتكامل **منصة ليلة** مع بوابات الدفع الإلكترونية المحلية المعتمدة في المملكة العربية السعودية (مدى، الفيزا/الماستركارد، و Apple Pay) وفق أعلى معايير أمان بيانات بطاقات الدفع (PCI-DSS).

```
+-----------------------------------------------------------------------------------+
|                     Lailah Secure Payment Flow & Gateway Architecture             |
+-----------------------------------------------------------------------------------+
|  [👤 العميل] ──► [تشفير إدخال الدفع PCI-DSS] ──► [إرسال مشفر للبوابة SSL/TLS 1.3] |
|                                                                                │
|  [تأكيد الحجز BKG وإصدار INV] ◄── [التحقق من HMAC] ◄── [إشارة الـ Webhook المشفرة]│
+-----------------------------------------------------------------------------------+
```

## 2. التحقق الرقمي المشفر من إشارات الـ Webhook (Cryptographic Webhook Validation)

تتعامل المنصة مع إشارات التأكيد المالي الواردة من بوابات الدفع عبر بروتوكول توثيق آمن لمنع التلاعب أو الهجمات والاحتيال المالي:

```
                  ┌───────────────────────────────────────────┐
                  │    محرك استقبال الـ Webhook المشفر        │
                  └─────────────────────┬─────────────────────┘
                                        │
     ┌──────────────────────┬───────────┴───────────┬──────────────────────┐
     ▼                      ▼                       ▼                      ▼
┌─────────┐            ┌─────────┐             ┌─────────┐            ┌─────────┐
│ قراءة   │            │ احتساب  │             │ مطابقة  │            │ فحص     │
│ التوقيع │            │ HMAC-   │             │ التوقيع │            │ المفتاح │
│ Header  │            │ SHA256  │             │ Digital │            │ Unique  │
└─────────┘            └─────────┘             └─────────┘            └─────────┘
```

### 2.1 خطوات تدقيق وأمان الـ Webhook
1. **استخراج رأس التوقيع الرقمي (Signature Header):** قراءة التوقيع المرفق في رأس إشارة الـ Webhook الواردة من بوابة الدفع.
2. **إعادة احتساب الـ HMAC-SHA256 بالسيرفر:** استخدام المفتاح السري المخفي بالسيرفر (`WEBHOOK_SECRET_KEY`) لاحتساب القيمة الرقمية المشفرة للبيانات الواردة.
3. **المطابقة الزمنية والدقيقة (Time-Constant Comparison):** مقارنة القيمة المحتسبة بالقيمة الواردة باستخدام اقتران مقارنة ثابت الزمان لمنع هجمات التوقيت (Timing Attacks).
4. **الرفض الفوري للطلب غير الموثوق:** إهفال الطلب وإصدار تنبيه أمني فوري في حال وجود أي اختلاف في التوقيع الرقمي.

## 3. محرك منع التكرار والخصم المزدوج (Idempotency Key Enforcement Engine)

تُطبق المنصة آلية حازمة لمنع الخصم المكرر أو قيد الحساب المزدوج عند حدوث مشاكل في الشبكة أثناء عملية الدفع:

```
[إرسال طلب التأكيد المالي] ──► [قراءة Idempotency Key المعين]
                                              │
       ┌──────────────────────────────────────┴──────────────────────────────────────┐
       ▼                                                                             ▼
(المفتاح لم يُعالج سابقاً)                                                   (المفتاح تم معالجته وتسجيله سابقاً)
       │                                                                             │
       ▼                                                                             ▼
[تأكيد الحجز BKG وإصدار الفاتورة INV]                                       [إرجاع النتيجة السابقة المسجلة فوراً دون خصم جديد]
```

## 4. سلامة العمولة وفصل الالتزام الضريبي

### 4.1 عمولة المنصة القابلة للتهيئة

لا تعتمد المنصة نسباً ثابتة للحزم؛ تحدد الإدارة المالية نسبة العمولة لكل باقة/خدمة نشطة ويمكنها تغييرها أو إضافة/تعديل الباقات. الأرقام الثابتة في النسخ السابقة ملغاة كالتزام وتعد أمثلة تاريخية فقط. يسجل النظام قيمة النسبة ومصدر إعدادها وإصداره وتاريخ سريانه مع لقطة الحجز/المعاملة. لا يقبل الحساب المالي نسبة افتراضية صامتة عند فقد الإعداد؛ يوقف المعاملة أو يستخدم fallback صريحاً معتمداً ومسجلاً.

### 4.2 فصل ضرائب الطرفين

ضريبة ليلة تخص عمولتها ومبيعاتها ورسومها الخاصة فقط. المزود مسؤول عن ضريبة الحجوزات والخدمات ومبيعات المنتجات والمستلزمات التي تخصه. لا تحسب ليلة هذه الضريبة لنفسها، ولا تسجلها إيراداً أو التزاماً ضريبياً عليها، ولا تصدرها عنه. يمكن إظهارها منفصلة للمزود أو للعميل في الإجمالي. لا تخلط قيمة الضريبة بعمولة ليلة أو مستحق المزود.

### 4.3 الفصل المالي لحملات التسويق

إذا نفذت وكالة خارجية الحملة، تفصل ميزانية الإعلان عن أتعاب الوكالة؛ عمولة ليلة المتغيرة على أتعاب الوكالة فقط، وضريبة ليلة على عمولتها. إذا تولت ليلة التسويق دون وكالة، تحصل تكاليف التسويق ولا تأخذ عمولة وكالة وتطبق ضريبتها وفق القرار المعتمد. إعلان ليلة داخل منصاتها خدمة تملكها وتديرها. لا تستخدم محفظة تسويات الحجوزات لتلك المبالغ، ولكل خدمة سجل مالي مستقل.

### 4.4 التحقق وعدم إحداث أثر مالي غير موثق

لا يكفي webhook صحيح وحده لتحديد استحقاق المزود أو ضريبة كل طرف. يربط كل تحصيل بالمعاملة والبنود ومالكها وإعداد العمولة ولقطة الضريبة، ويمنع إنشاء أثر مالي مكرر أو من مسار غير معتمد. يجب أن تعكس القيود العكس/الاسترداد على البنود الأصلية وبالنسب نفسها.

## 5. حوكمة الرقم التسلسلي الموحد والربط المالي الشامل

- **شاملية الإحصائيات والتحليلات المالية:** احتساب وتدميج حجوزات القاعات وطلبات الخدمات المساندة معاً في جميع الإحصائيات والمؤشرات المالية والتدفقات النقدية والتقارير.
- **التسلسل الموحد (تصفير سنوي من `0000000001`):**
  - **حجوزات القاعات:** `BKG-YY-XXXXXXXXXX` (مثال: `BKG-26-0000000001`).
  - **طلبات الخدمات:** `SRV-YY-XXXXXXXXXX` (مثال: `SRV-26-0000000001`).
  - **الفواتير الصادرة الموحدة:** `INV-YYXXXXXXXXXX` (مثال: `INV-260000000001` بدون واصلة بعد السنة).
  - **الإيرادات المالية:** `REV-YY-XXXXXXXXXX` (مثال: `REV-26-0000000001`).
  - **المصروفات المالية:** `EXP-YY-XXXXXXXXXX` (مثال: `EXP-26-0000000001`).
